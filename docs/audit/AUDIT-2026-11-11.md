## 3. Ranked blockers and findings

Severity: CRITICAL = data loss or wrong-DB write risk. HIGH = blocks a go-live step. MEDIUM = correctness or governance gap. LOW = documentation or cleanliness.

### F1 — HIGH (live-blocking if the feed is compress). `.Z` ingestion is not supported.
- Evidence: `engines/psx_feed_parser.py:64-66` uses `zipfile.ZipFile` only. `engines/psx_exports.py:90-112` tries ZIP and gzip, then falls through to plain text. No LZW or `compress` decoder exists anywhere (`grep` for `x1f\x9d`, `lzw`, `uncompress` finds only `psx_exports.py`, where the match is a comment).
- Supplied files: both are ZIP archives. Magic bytes `PK\x03\x04` (`58860e0b-announceWithSymbol.lis.Z`, `590eb050-listed_cmp.lst.Z`), consistent with `docs/PSX_EXPORT_FORMATS.md:3`.
- Synthetic check (no real data): a UNIX `compress` header (`1f 9d`) gives `psx_feed_parser.load_announcements` a `BadZipFile` error (fails loudly), but `psx_exports.parse_announcements_report` returns **0 records and 1 log line** (fails open).
- The brief states the live feed is compress/LZW. This repository holds no live sample and no feed URL, so that premise is **UNKNOWN**.
- Impact: the runner would fail loudly on compress, but the `psx_exports` path would drop the feed silently.

### F2 — HIGH. Migration 0016 lacks the mandated provenance fields.
Missing from `psx_financial_results` (archive analogues in `database/archive_migrations/0001` and `0005`):
1. Source document SHA-256 (archive: `archive_reports.report_sha256`).
2. PDF page or evidence reference (archive: `archive_line_items_v2.pdf_page_number`).
3. Source label or text (archive: `archive_line_items.raw_label`).
4. Extractor version (archive: `archive_extraction_runs.extractor_version`).
5. Consolidation scope (archive: `scope`, `consolidation`).
6. Basis, reported or restated (archive: `basis`).
7. Explicit unit per fact (archive: `unit`; 0016 has `scale` only).
8. Filing or publication date (absent everywhere in the PSX path).
9. Validation or confidence status (absent; only free-text `warnings`).
10. Run or evidence identifier linking facts to a run (absent).
- Evidence: `database/migrations/0016_psx_financial_results.sql` column list; `engines/pucar_statement_parser.py` returns only `warnings`.
- Consequence: a stored PKR figure cannot be traced to a page, a document, or an extractor version.

### F3 — HIGH. Reconciliation statuses are incomplete and inconsistent.
- News: `database/migrations/0016_psx_financial_results.sql` allows only `('reconciled','no_figures')`.
- `engines/financial_reconciler.py:50-56` sets `reconciled` whenever any figure exists, regardless of warnings. A statement with "period length not stated" or "currency is USD" is still `reconciled`.
- The brief's required set (`reconciled`, `no_figures`, `not_verifiable_from_disclosure`, `unmapped`, `requires_review`) is not in the schema. The repo's `NOT_VERIFIABLE_FROM_DISCLOSURE` exists only as engine output (`engines/cash_equivalents.py`), not as a stored status.
- Archive vocabulary (`archive_migrations/0005_extractor_versioning.sql:60`): `RECONCILED`, `RECONCILED_WITH_ROUNDING`, `UNRECONCILED`, `INSUFFICIENT_DATA`. The two systems use different vocabularies for the same concept.

### F4 — MEDIUM (brief) / conflicts with repo strategy. Runner ignores holidays and after-hours policy.
- `engines/termux_node_runner.py` gates on Mon–Fri 09:00–16:30 PKT. It has **0** references to the calendar or holidays.
- `docs/COLLECTION_SCHEDULING_STRATEGY.md:29,83` says "no routine weekend polling" and "one after-close run and one overnight run". The brief asks for economical after-hours polling. These two requirements conflict and need an owner decision.
- `docs/PSX_CALENDAR_MAINTENANCE.md` records holidays and regular hours. The runner does not read it.

### F5 — HIGH. Financial facts are in the news DB; the archive is the designated home.
- The news DB receives three PSX financial tables from branch migrations and four more from `main`:
  - From `main`: `financial_reports`, `financial_line_items`, `account_mappings` (`0011`), `valuations`, `dimension_assessments` (`0012`).
  - From the branch: `psx_financial_results`, `psx_reconciliation_status` (`0016`).
- `psx_announcements` (`0015`) is a thin event record (metadata, no PDFs). Placing it in news is consistent with `MASTER_ARCHITECTURE` L1.
- `psx_financial_results` is archive-class data: statement-level facts with no provenance. It belongs in the archive, through a new additive archive migration (`archive_migrations/0006_*`), not by editing `0016`.
- Duplication or conflict: the news `financial_reports` and the archive `archive_reports` describe the same domain with no cross-DB reconciliation. Divergence is possible and not detected.
- Routing: `engines/financial_reconciler.py:24-46` takes a caller-provided `Database`. No caller is wired, so writes today are test-only.

### F6 — HIGH. The role guard does not catch financial tables in the news DB.
- `database/connection.py:306-307`: `OPERATIONAL_TABLES = ("source_items","companies","events","market_bars")`; `ARCHIVE_TABLES = ("archive_reports","archive_financial_tuples")`.
- The news DB has about 100 tables; the archive has 13. The guard would not refuse a news DB holding `financial_reports`, `psx_financial_results` or `valuations`, nor an archive DB holding `archive_disclosures`.
- The guard is enforced at `connection.py:333-338` only when a connection is opened. It is not derived from the migration directories, and no test asserts the lists match the schema.
- This is the gap class that enabled the 0011 incident. Its closure is **not verified** (Workstream G).

### F7 — MEDIUM (architecture conflict; not a permission question). SCS OHLCV storage.
- `database/migrations/0010_market_ohlcv.sql` creates `market_bars` in the news DB. `collectors/market_ohlcv.py:3` names `chart.scstrade.com` as the provider.
- `docs/MASTER_ARCHITECTURE.md:36` and `docs/MASTER_DATABASE_DESIGN.md:22` place `market_bars` in the operational raw store, and `MASTER_DATABASE_DESIGN.md:56` uses it as an input to `valuations`.
- The brief places SCS price data in the Technical system (spec 11). **No repository document says that.** The conflict is between the brief and the repo docs; the owner must resolve it.
- ADR-0001 forbids sharing data with the technical project, so a copy in news is not a duplicate of a shared table. Whether the technical DB also holds SCS bars is **UNKNOWN** (it is out of scope).
- Collection is not affected by this finding. Only storage location is.
